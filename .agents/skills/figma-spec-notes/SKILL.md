# Figma Spec Notes

Скил пишет содержательную спецификацию к готовому макету и размещает её не отдельным документом и не аннотациями, а **текстовыми блоками прямо на холсте Figma, рядом с той частью макета, которую они описывают**. Итог выглядит как пара «кусок макета + текст сбоку/снизу от него».

## Когда использовать

- Пользователь выделил фрейм(ы) в Figma и просит написать/задокументировать логику
- Пользователь прислал скриншоты макета и просит "спеку", "описание", "документацию к экрану"
- Нужно зафиксировать состояния, условия показа, edge cases готового дизайна рядом с самим макетом, в удобном для чтения на холсте виде

Не использовать, если макета нет вообще — сначала попросить выделить фрейм в Figma (дать ссылку с node-id) или приложить скриншоты.

## Технический принцип работы

Скил не использует Comments API (недоступен через `Figma:use_figma`) и не использует Dev Mode Annotations. Вместо этого он:

1. Дублирует нужную часть макета (или берёт исходный фрейм как есть) в виде отдельного фрейма-секции на холсте
2. Рядом с этой копией (справа или снизу — в зависимости от компоновки исходного макета) создаёт текстовый блок с описанием этой части
3. Группирует пару «фрагмент макета + текст» в один frame, чтобы они не расходились при дальнейшем редактировании

Это соответствует структуре референса: сначала кусок макета, сразу под/рядом с ним — абзац текста, поясняющий этот кусок.

## Шаг 1. Собрать входные данные

Прежде чем анализировать макет и писать что-либо, проверить наличие:

1. **Макет(ы)** — обязательно. Ссылка на фрейм(ы) в Figma (`fileKey` + `nodeId`) или скриншоты. Без этого не начинать.
2. **Все состояния макета** — прислал ли пользователь пустое/ошибочное/загрузочное состояния или только "счастливый путь". Если только одно — прямо спросить, есть ли другие, а не додумывать.
3. **Аналитика/данные** — данные о частоте кейсов, приоритетах сортировки, планах A/B-теста. Если нет — не выдумывать, помечать как открытый вопрос.
4. **Пользовательский сценарий** — откуда пользователь попадает на экран и что происходит после (если не считывается с макета однозначно).
5. **Ограничения/зависимости продукта** — существующие компоненты дизайн-системы, интеграции, влияющие на логику.

Если по пунктам 2–4 ответа нет и он не выводится из макета — не блокировать работу, но помечать соответствующий текстовый блок как открытый вопрос (см. Шаг 4).

Задавать уточняющие вопросы одним заходом, не растягивая на несколько сообщений.

## Шаг 2. Разобрать макет на смысловые блоки

Работать с макетом так, как его видит пользователь, а не по слоям Figma:

1. Выделить смысловые блоки макета (шапка, CTA, список, состояние ошибки, блок с кнопками и т.д.) — именно эти блоки станут единицами «фрагмент + текст рядом»
2. Для каждого блока определить: что показано, какие данные динамические, какие тексты — реальный контент или плейсхолдер
3. Зафиксировать только те состояния компонентов, что реально присутствуют в макете или явно описаны пользователем
4. Всё, что нельзя вывести из макета и не проговорено пользователем — превращать в открытый вопрос, не додумывать

## Шаг 3. Определить содержание для каждого текстового блока

Два типа текстовых блоков:

**Общий блок** (один текст рядом с макетом целиком, обычно слева или сверху от всей композиции):

- Цель/проблема
- Скоуп / Вне скоупа
- Общее описание
- Пользовательский флоу
- Метрики успеха (если есть данные)

**Блоки по фрагментам** (свой текст рядом с каждым смысловым куском макета):

- Условия появления / триггеры — рядом с элементом, который показывается по условию
- Состояния — рядом с фрагментом, где показан конкретный вариант состояния (таблица «состояние → условие → поведение» как список в тексте)
- Детализация блока — состав, лимиты символов, сортировка, источники данных
- Edge cases и обработка ошибок — рядом с элементом, где может возникнуть ошибка/пустое состояние
- Открытые вопросы — рядом с тем фрагментом, к которому относится вопрос; если вопрос общий — в общем блоке

## Шаг 4. Пометка открытых вопросов

Текстовые блоки с открытыми вопросами или местами, где не хватило входных данных, должны явно начинаться с маркера:

- `[ОТКРЫТЫЙ ВОПРОС]` — логика не решена, нужен ответ продукта/дизайна
- `[TODO: уточнить]` — не было передано на входе, додумывать нельзя

Не смешивать эти маркеры с текстом решений в одном блоке — если в куске есть и решённая часть, и открытый вопрос, разносить их на два отдельных текстовых блока рядом друг с другом.

## Шаг 5. Проверить существующий формат оформления в файле

Перед созданием текстовых блоков проверить, есть ли в этом же Figma-файле уже сложившийся стиль (похожие текстовые описания рядом с другими макетами этого продукта — их шрифт, размер, отступ от макета, наличие заголовков разделов). Если шаблон найден — повторять его визуальный стиль и структуру подачи (как в референсе: фрагмент макета сверху, абзац текста под ним, изредка — жирный подзаголовок раздела). Если нет — использовать дефолтный формат: текстовый фрейм шириной ~400px, с заголовком раздела жирным (`Состояния:`, `Edge case:`) и текстом обычным начертанием под ним, отступ 24–40px от края фрагмента макета.

## Шаг 6. Показать черновик и получить апрув

Прежде чем что-либо записывать в Figma, собрать все подготовленные тексты (общий блок + блоки по фрагментам, включая маркеры открытых вопросов) и показать их пользователю в чате как черновик — по каждому блоку: к какому фрагменту макета он относится и какой текст предполагается разместить рядом.

- Не вызывать `Figma:use_figma` для записи, пока пользователь явно не подтвердил черновик
- Если пользователь просит правки — вносить их в черновик и показывать обновлённую версию снова, до получения явного согласия
- Явное согласие — это подтверждение в духе "ок", "апрувю", "пойдёт", "давай" и т.п. Молчание или смена темы не считается апрувом

Только после явного апрува переходить к следующему шагу.

## Шаг 7. Разместить фрагмент макета и текст на холсте

Использовать `Figma:use_figma` с кодом на Figma Plugin API.

Порядок действий в коде:

1. Получить исходную ноду макета/блока через `figma.getNodeByIdAsync(nodeId)`
2. Если нужно показать именно этот фрагмент отдельно (а не весь макет целиком) — либо сослаться на исходную ноду по месту (без копирования, если фрагмент и так стоит отдельно), либо клонировать нужный под-фрейм через `node.clone()` и разместить копию на пустом месте холста рядом с общей композицией
3. Создать текстовый узел: `const text = figma.createText()`, обязательно сначала загрузить шрифт — `await figma.loadFontAsync({ family: "Inter", style: "Regular" })` (и отдельно "Semi Bold" для заголовков, если нужен жирный)
4. Задать текст через `text.characters = "..."`, положение — через `text.x` / `text.y`, ширину — через `text.resize(width, height)` или auto-layout
5. Расположить текстовый блок рядом с фрагментом: если у фрагмента есть свободное место справа — размещать там, иначе — снизу
6. Обернуть пару «фрагмент + текст» в общий frame через `figma.group([...])` или создание нового auto-layout frame с обоими элементами внутри, чтобы они не разъезжались при перемещении

Пример кода (адаптировать под конкретные найденные ноды и координаты):

```javascript
await figma.setCurrentPageAsync(page);

// Загрузка шрифтов заранее
await figma.loadFontAsync({ family: "Inter", style: "Regular" });
await figma.loadFontAsync({ family: "Inter", style: "Semi Bold" });

// Исходный фрагмент макета (например, блок "Состояния")
const sourceNode = await figma.getNodeByIdAsync(fragmentNodeId);

// Текстовый блок рядом
const textNode = figma.createText();
textNode.fontName = { family: "Inter", style: "Regular" };
textNode.characters =
  "Состояния:\n" +
  "— тариф срочный: осталось ≤30 дней поставки\n" +
  "— тариф ресурсный: осталось ≤10 документов\n" +
  "— тариф истёк: поставка закончилась, показываем отдельный текст";
textNode.resize(320, textNode.height);

// Позиционирование справа от фрагмента с отступом 32px
textNode.x = sourceNode.x + sourceNode.width + 32;
textNode.y = sourceNode.y;

// Группировка, чтобы пара не расходилась при переносе
const pairFrame = figma.group([sourceNode, textNode], figma.currentPage);
pairFrame.name = "Состояния — фрагмент + описание";
```

Для общего блока (цель, скоуп, флоу) — тот же принцип, но текст размещается рядом с макетом целиком (слева или сверху от всей композиции), без группировки с исходным фреймом, чтобы не ломать его структуру.

После размещения — сообщить пользователю коротким списком, какие текстовые блоки и рядом с какими фрагментами добавлены, без дублирования полного текста в чате (если блоков много — по одной строке на блок).

## Что не делать

- Не записывать текстовые блоки в Figma, пока пользователь явно не подтвердил черновик текста в чате
- Не создавать отдельный .md/.docx файл со спецификацией — результат живёт на холсте Figma рядом с макетом
- Не использовать Dev Mode Annotations и не пытаться создавать комментарии-пины — только видимые текстовые блоки на холсте
- Не выдумывать состояния, лимиты, аналитику, которых нет на макете и не подтверждены пользователем
- Не смешивать решённое и открытые вопросы в одном текстовом блоке
- Не перекрывать текстом другие элементы макета — всегда оставлять текст на свободном месте рядом с фрагментом
- Не игнорировать уже существующий в файле формат оформления, если он есть
